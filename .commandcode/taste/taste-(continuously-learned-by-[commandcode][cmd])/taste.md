# Taste (Continuously Learned by [CommandCode][cmd])
- Prefers evolving specs/plans as a new versioned document (e.g. "API Test Plan v0.4.md" → "v0.5.md") rather than editing the existing file in place — prior versions are kept intact, and the new doc notes what it supersedes. Confidence: 0.8
- Prefers self-contained documents: merged content (e.g. a reconciliation addendum) into the main plan with a changelog/change table, rather than maintaining separate companion files — duplicate/stale companion files should be deleted, relying on git history to preserve them. Confidence: 0.7
- Prefers reference material kept in a tool-readable, in-repo text form (e.g. a markdown catalog/table) rather than opaque binaries (e.g. an `.xlsx` workbook), so cited IDs resolve in-repo. Confidence: 0.55
- Commits document changes as separate, chronologically distinct commits rather than one combined commit — e.g. commits the base/original version first, then the later modification as its own follow-up commit. Confidence: 0.6
- Values durable domain documentation alongside code/docs: a `GLOSSARY.md` pinning overloaded domain terminology and ADRs recording significant, hard-to-reverse decisions (e.g. "captured responses are the source of truth"). Confidence: 0.5
- Prefers the vendor-neutral `AGENTS.md` convention at the repo root over vendor-specific ones like `CLAUDE.md`. Confidence: 0.5
- Tracks issues/work in GitHub Issues driven by the `gh` CLI (GitHub `origin` remote) working with the canonical/default triage conventions rather than custom label vocabularies. Confidence: 0.45
- When requesting new test cases, expects them grounded in the sample requests/docs already in the repo — reuse the existing request shapes/formatting rather than inventing fixtures from scratch. Confidence: 0.55
- Expects test coverage to include combinations of varying inputs (e.g. different coverage, vehicle and driver combinations), not just single-variable cases. Confidence: 0.5
- Prefers work scoped tightly to the explicitly stated requirement: keep the stated priorities as the focus and defer/skip ambiguous or unlisted items ("skip these for now") rather than expanding coverage into them speculatively. Confidence: 0.55
- Treats in-repo sample requests/data as formatting references only — their content can be outdated or inherited from other vendors and is not authoritative for scope; the written requirement governs. Confidence: 0.5
- When a deliverable is meant for a manager/auditor, expects it to conform to a recognized formal standard (e.g. ISO/IEC/IEEE 29119-3 test-plan structure) with document-control sections: document ID/version/status, revision history, approval/sign-off block, entry/exit and suspension/resumption criteria, and requirement→case traceability. Confidence: 0.6
- Wants to be interviewed with targeted clarifying questions (deliverable format, scope, numbering, conformance standard) before the agent commits to producing a significant document — prefers being asked up front over the agent assuming. Confidence: 0.6
- Wants audience-tailored deliverables: when a document is meant for a manager/stakeholder audience, prefers a separate condensed executive-summary copy (~1–2 pages, decision-oriented, minimal jargon, dropping appendices/traceability detail) that links back to the full detail doc, leaving the full doc unchanged rather than trimming it in place. Confidence: 0.5
